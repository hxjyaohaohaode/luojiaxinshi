# 面向学生的通知聚合与查看

目标是让学生从自己已接收的学校、学院及其他来源通知中，先看清出处、原文和是否需要本人进一步核对，再决定是否建立个人待办。数据归当前账号所有；来源显示不代表系统替学校认证了发布者。

## 怎么使用

1. 在“通知资料”顶部查看网站订阅概况；展开“查看详情”后可以看到各来源是否开启、最近检查时间、是否仍在读取或出现问题。入口只汇总网站订阅状态；QQ 群和公众号等渠道需到“通知来源”查看各自授权与状态。
2. 点击“检查新通知”可逐个检查当前账号**已开启自动接收**的网站来源，并在完成后刷新本人的通知列表。未开启、已暂停的网站不会被自动启用。一次最多检查 20 个，检查失败或仍有积压会说明；来源页可查看详细原因。此按钮复用现有收件链路，不会直接创建或完成待办。是否调用模型仍由用户在来源设置中单独控制。
3. 用“按来源查看”筛选学校、学院或本人其他来源；一则通知由多个来源转入并已合并时，各来源都可以找到它。来源名称可能由用户填写，不据此赋予官方认证标记。
4. 默认按原记录的发布时间从新到旧排列，发布时间未知的放在后面；也可切换按收录时间或最近更新。页面分别标出发布与收录日期。多来源合并时，显示的是原记录的发布时间，不把后续转发日期冒充为原始发布时间。
5. 卡片显示原文节选，明确标记来源更新或材料需核对；节选不是模型摘要，可能不包含完整要求。打开通知后应继续查看原文、附件、适用条件和日期。只有本人核实后才将需要的步骤转成待办。

“要核实”包含尚未判断适用性或有变化待核对的通知，不代表每则都与本人有关；也不代表已经阅读或完成。只为简化界面，收件概览暂时隐藏数量为零的类别，出现相关记录后会自动显示。

## 接口与兼容

`GET /api/notices` 和 `/api/notices/search` 在既有字段上增加 `published_at`、`origin_labels`、`source_excerpt` 和 `source_review_count`。来源名称从当前账号的收件记录汇总；没有收件记录的旧数据沿用原来源或显示“个人提交”。只使用有效材料的原文段落作为节选，不能解析的材料会保留需核对标记。搜索覆盖同一通知的各个来源名称。

打开页面本身不创建数据表、不修改已有通知，也不会自动新增订阅或发起检查；原有已启用的后台同步仍按设置运行。学生主动点击检查时，仍执行原网站订阅的权限、频率、公开地址和去重规则；手动刷新受原接口每小时次数限制，来源较多时应分批检查。

分权、收件隔离和数据备份仍按[学院身份与定向通知](CAMPUS_PERMISSIONS.md)、[通知接入与办理](NOTICE_FLOW.md)执行；真实网站结构、目标设备推送和真实学生使用效果需分别验证。
