# MVP 办理闭环与演进契约

版本：1.14.1。更新：2026-10-19。本文是随代码维护的工程说明。

验收依据为原始赛题、《校园通知智能转办助手_最小可行版本_小米模型版_2026-10-14.docx》及完整设计方案。用户本轮明确优先处理“办理闭环、变更与未来扩展不足”。运行结果及外部验收边界见 [TESTING.md](../TESTING.md)。

1.10.0 增加维护者启用、用户按次选择的加速整理，继续保留来源复核、条件与依赖检查、变更一致性和人工确认。一次完整调用约 39 秒，仍有语义意见需要处理，不能因此将“流程完成”计为“提取全对”。费用、失败样本和限制见 [ADR-007](ADR-007-notice-processing-modes.md)。

1.11.0 将复核后的本人处理改为逐条记录，检查实际改动、所选步骤与原草稿的关系，保留不采纳意见的依据。处理结果可直接回看，并以历史记录随个人 JSON 迁移；导入不代表重新核实。见 [ADR-008](ADR-008-per-issue-human-resolution.md)。

1.12.0 增加核对页面用时的有界观测，随确认与历史迁移保存，统计范围见 [ADR-009](ADR-009-review-time-observation.md)。原方案剩余的外部验收门槛见下文“原方案尚待外部验收的门槛”；原逐项映射文档已移除，见 git 历史。

## 本轮纠正的问题

原实现具备资料、对话、草稿与日历，但首页与交互重心偏向回答生成。待办只有完成／取消不足以表达提交、补件、受阻和等待结果；重新整理要求也不应重置个人安排。通知更正需要先核实影响范围，不能直接替换旧期限。导出 ICS 更不能代表设备已经导入或收到提醒。

当前首页改为办理工作台。正式要求、个人办理记录、外部变更提案和设备验证分别管理。聊天与互动回答继续服务于资料理解；进入正式待办仍须经过本人确认。

## 数据与状态规则

`tasks.data` 继续保存现有 `TaskData`，兼容当前日历、草稿和导出。正式字段与个人字段目前通过写入白名单和保留规则隔离，没有为此次改版拆散已有待办。

办理模块使用以下数据表：

- `task_workflows`：每项任务的办理记录、材料准备、依赖、回执和跟进；有独立版本。仅勾选材料不会无故改变日历版本。
- `notice_changes`：原始变更来源、选择范围、预期通知与待办版本、待确认／已应用／已排除状态。提案保存本身不改变任何正式要求。
- `calendar_checks`：本人记录的设备、实际结果、时间和对应任务版本。这里只记录本人验证结论，没有实现日历平台送达回执。
- `task_reviews`：变化来源、累计待核对字段、独立复核版本、本人结论及依据。复核状态独立于历史完成和学校受理。
- `arrangement_receipts`：当前账号的安排创建标识、安排 ID 与创建时间。同事务触发器覆盖普通创建和 JSON 导入；安排删除后仍用于识别已完成的旧提交，不保留标题、地点或备注。删除账号时级联清理。

日历草稿恢复先查询创建状态，明确区分未保存、已保存和已删除；查询只返回本人记录的当前版本。查看记录继续保留草稿，另建与清空后新建均需本人选择并分配新的提交标识。网络错误不能推断正式写入失败；迟到查询受账号、页面和弹窗归属检查。删除后的同一创建请求返回冲突，不会自动重建。

页面文件可能早于后台进程完成更新。状态接口返回 404 时，只有健康检查明确报告兼容的旧版 1.x（早于 1.14.1），才保持原有草稿编辑并提示到日历自行核对。当前版本的 404、503、健康检查失败或未知版本继续按无法核对处理，不能伪装成未保存。旧进程没有新增的删除防重建能力，必须分别核对代码版本与实际服务版本。

创建记录使用独立结构版本 `arrangement_receipt_schema_version=1`。旧库为仍存在的安排补齐，重复启动不重复写入；升级前已删除的记录无法从现状追溯。不支持的结构版本或带版本标记但缺表时拒绝启动和恢复，不能静默将未知状态当成未创建。

数据库以 `workflow_schema_version=2`（从 1 增量升级） 和 `action_review_schema_version=1` 执行增量创建，主数据版本仍为 4。旧数据自动获得空办理记录；无删库、清表或强制重建。高于当前支持范围的办理／复核数据版本会拒绝开启或恢复，防止静默降级。

通知变更应用在同一 SQLite 写事务内完成：核对所有版本、保存变更原文、更新明确选择的任务、保留个人数据、协调材料勾选、记录前后值、使旧草稿失效。任一事项冲突则整批回滚。取消不视为完成；恢复也不代表自动提交。删除通知时级联清理相应执行、变更和设备验证记录。

新增要求不会自动勾选为已准备。已移除材料的旧勾选会从数据库清除，未来重新加入同名材料也必须再次核对。

复核需要先处理前置的待复核状态；选择“保留原进度”需要本人说明当前适用依据，选择“重新办理”恢复待完成并保留原回执。删除前置通知前传播影响，避免更后面的历史完成掩盖缺失的前提。未开始且没有个人安排的简单改期不额外要求重复确认。旧数据库没有记录过的变化不伪造历史复核，详细取舍见 [ADR-002](ADR-002-action-change-review.md)。

### 迁移的两种用途

SQLite 备份适合本机／服务器完整恢复，保留原 ID、依赖、变更、设备记录及安排创建记录，恢复时沿用已有安全流程清除会话和授权。必须恢复到新的空目录。个人 JSON 不携带已删除安排的创建记录；导入仍存在的安排会分配本账号的导入标识并生成对应创建记录。

个人 JSON 导入适合追加迁移，不能覆盖原数据。附件原件不包含在 JSON 中，期限要重新核对，提醒时间清空。办理记录和回执保留；条件文字和原核实说明保留，状态重置为待核实。同一账号按导出记录的原标识连接前置关系，同次或分批导入都可恢复。找不到的前置项明确标为缺失，仍可记录准备与跟进，但不能越过它提交或完成。循环关系使整批回滚，跨账号记录不参与匹配。导入去重继续按通知标识判断；不能靠修改通知标识覆盖已经导入的同源待办。

待复核状态、已复核结论及本人说明同样保留，来源按当前账号重新绑定；缺失来源显示为待补齐，不访问原账号记录。分批导入补齐来源时增加复核版本，使旧表单失效。

`import_task_links` 是导入模块的辅助映射表，随导入模块增量创建，记录当前账号的原任务标识与新任务标识；完整备份会携带此表。待补齐关系再次导出、导入时保留稳定占位标识，不重复散列导致丢失连接。已处理变更保留当时的前后值、核实结论和原时间；连续迁移不会用后来的任务值改写历史。原待确认变更降为待核实线索，不能直接执行。设备验证需要重新进行。

JSON 不是完整数据库镜像：旧版本文件中本来没有的审计前后值无法从当前任务反推，原始附件也须重新补充。需要完整历史和原件恢复时使用 SQLite 备份。

## API 契约

所有入口继续受登录、账号归属、CSRF 和请求校验保护。客户端不得通过字段补丁修改个人备注、计划、提醒或越过版本约束。

| 接口 | 用途 |
|---|---|
| `POST /api/notices/{id}/confirm` | 选中任务与 `plans` 同事务确认；依赖为选中步骤序号，更新原办理安排须当前办理版本 |
| `GET /api/tasks/{id}/workflow` | 当前办理记录、本人可选前置事项和时间线 |
| `PUT /api/tasks/{id}/workflow` | 带任务版本和办理版本保存真实进度 |
| `POST /api/tasks/{id}/change-review` | 带任务和复核版本保存本人依据，保留进度或重新办理 |
| `POST /api/notices/{id}/changes` | 记录变更提案及明确目标，不立即写正式任务 |
| `GET /api/notices/{id}/changes/{change_id}` | 待确认影响预览；已应用时读取当时审计前后值 |
| `POST /api/notices/{id}/changes/{change_id}/decision` | 本人核实后应用或排除；重放不重复写入 |
| `POST /api/tasks/{id}/calendar-check` | 保存当前版本的本人设备验证结论 |
| `GET /api/arrangements/requests/{request_id}` | 只读核对本人创建状态：`missing`、`saved`（当前安排版本）或 `deleted`；不泄露其他账号是否使用该标识 |
| `GET /api/auth/policy` | 无需登录，只返回公开／受邀注册模式；注册时仍由后端校验邀请 |

通知详情返回 `changes`；待办返回 `workflow`、`change_review`、`schedule_issues`、`pending_changes`、`followup_due`、`calendar_check` 和 `calendar_check_required`。`needs_calendar_sync` 表达旧导出版本需要更新；`calendar_check_required` 表达实际导入仍待本人核实。工作台同时关注这些情况，已完成但待复核的事项也进入“变更待核实”筛选。

## 与完整版的衔接

| 后续能力 | 可复用的已实现基础 | 上线前仍需完成 |
|---|---|---|
| 更多官方来源与渠道 | 现有来源目录、原件存储、账号归属；变更提案与来源依据 | 各渠道合法授权、稳定外部 ID、来源认证及实际联调；采集结果不能直接应用变更 |
| 同通知多次更正与版本关系 | 原通知稳定 ID、版本、不可直接执行的变更记录、历史审计 | 跨来源匹配／置信度与人工消歧；学期、批次不明不能自动合并 |
| 更细的个人行动图 | 同账号跨通知前置关系、循环检测、独立执行记录、本人参加意愿与外部条件 | 通用条件表达式、自动分支与可选路径、材料复用权限与重排策略；规划建议仍由本人确认 |
| 自动调度和可靠推送 | 跟进时间、任务版本、导出版本、独立验证结果 | 持久队列、渠道授权、撤回与去重、重试策略、供应商送达证据；当前只有站内跟进和 ICS |
| 校内系统提交与受理回执 | 本人提交记录、结果、补件原因、回执链接、审计 | 校方 API 和身份权限、操作确认、请求幂等及补偿；当前没有自动代办或伪造学校受理 |
| 多人／院系使用 | 账号隔离、事务、版本冲突、恢复流程 | 真实部署压测、权限角色和组织范围、运营告警及隐私评估；不能从合成小规模测试推断校园容量 |

未来适配器先输出原始材料或变更候选，再复用核实与执行流程。未来提醒模块可以消费当前任务版本和跟进时间，但不得把“任务已导出”升级成“通知已送达”。没有为了未来可能性预先引入空服务、消息队列或另一套前端框架。

## 原方案尚待外部验收的门槛

工程测试不能代替原 MVP 指定的真实验收。下表是后续执行入口，不是已取得的结果；当前凭证状态、设备与样本证据以 [TESTING.md](../TESTING.md) 为准。

| 验收内容 | 原方案要求及证据 |
|---|---|
| 小米模型真实联调 | 有效凭证下逐模型验证文字／图片提取、ASR、普通播报、音色设计与获授权声音复刻；记录请求结果、时延、用量和失败。模拟服务不计入真实成功 |
| 真实通知质量 | 至少 10 份开发通知、20 份独立冻结测试通知，覆盖三类业务与边界条件；保留八类事实、行动和期限的人工作准，分别统计正确、遗漏、错误与失败／手工回退 |
| 真实学生完整流程 | 至少 5 位学生，每人完成本项目、手工处理、通用 AI 三种条件，各 2 份匹配但不同的通知；轮换顺序，计入核对、更正、日历操作时间，保留每人差异、中位数和失败 |
| 手机提醒 | 在目标手机验证新建、重复导入、改期、取消、关闭页面与锁屏；保存设备、日历、权限与实际结果。尚无一条渠道验证成功时，只能称通知整理原型，不能宣称提醒闭环已验收 |
| 真实场景使用 | 至少 5 个实际使用日，保留逐日问题、处理和结果记录；工程合成账号、重复同日操作不能代替真实参与者和使用日 |
| 试点环境与资源 | 明确样本和参与者来源、使用权限、设备及维护责任；跨设备使用需实际可达的 HTTPS 服务，受邀试点部署应启用邀请模式 |
| 交付形式确认 | 发榜单位确认通知处理智能体、手机网页工作台和个人待办看板的交付形式，以及样本范围、测试标注、计分和通过条件 |

这些门槛不能由代码或合成数据凭空完成。当前可以交付的是已实现并有工程证据的功能，以及能逐项继续验收的记录路径。

## 复验

```powershell
.\.venv\Scripts\python.exe -m pytest -q --junitxml=artifacts/mvp-acceptance/backend-final.xml
node --test tests/*.test.mjs
.\.venv\Scripts\python.exe -m pip check
```

`scripts/mvp_preview_server.py` 仍可启动隔离的合成数据服务，仅监听 `127.0.0.1:8780`，数据写入被 Git 忽略的 `artifacts/mvp-acceptance/data`，不会读取正式数据或使用模型密钥。当时配套的页面、弹窗、流程、竞态和内容浏览器脚本已在 1.20.0 清理，见 git 历史；当前浏览器回归统一运行：

```powershell
.\.venv\Scripts\python.exe scripts/run_browser_checks.py
.\.venv\Scripts\python.exe scripts/run_agent_browser_checks.py
```

`scripts/verify_notice_model.py` 明确使用本机配置发起一次合成文字通知的真实模型调用；只在需要验证凭证时主动运行。
