# Agent 记忆项目源码审查与选型

审查对象来自用户提供的“推荐Agent记忆项目”聊天。下载固定到 GitHub 提交版本，压缩包存于 D:\项目文件\SKILL，解压目录存于 D:\项目文件\SKILL_extracted。LangGraph 作为 LangMem 的配套状态与存储框架一并审查。所有结论对应表中固定版本，不自动代表上游以后版本。

## 1. 审查覆盖与证据边界

共核对 13 个仓库、24,939 个文件，其中 23,873 个 UTF-8 文本文件共 6,339,106 行，压缩包合计 496,646,354 字节。每个解压文件均完整读取并计算 SHA-256，比较原下载清单；压缩包核对哈希及 ZIP CRC；文本全量扫描生命周期、检索、权限、持久作业、人工修改和来源线索，Python 文件进行语法与定义索引。

在全量清单基础上，对各仓库的核心写入、召回、更新、删除、整理、授权接口、配置和相关测试进行了重点审读。审查结论结合实际代码路径，不只依据 README 宣传。逐文件证据保存在 full-file-audit.jsonl，整体统计保存在 full-audit-summary.json，完整提交号、下载地址和压缩包哈希保存在 sources-manifest.json。

全量静态扫描不等于逐行人工理解 633 万行，也不等于运行了全部上游测试或完成安全认证。本次没有执行外部仓库的安装钩子、样例服务或测试套件；符号链接作为惰性文本落盘，避免解压时创建越界链接。OpenViking 的一个 27 字节链接占位文件被 Python 语法扫描标记，属于这种处理的预期结果，不能据此认定其上游代码有语法错误。

## 3. EverOS：主要参考

技术：Markdown 记忆文件、SQLite 元数据和 LanceDB 检索结合，区分用户记忆与 Agent 记忆；级联流程包含文件监听、持久队列和对账扫描；反思流程将选择、合并、重新提取和旧内容退役分阶段处理。

优势：可编辑文件与结构化索引并存，来源和增量整理路径清晰；对账器能够补回文件监听漏报，并处理删除与暂时读取失败。适合借鉴为用户可理解、Agent 可维护的记忆层。

代价与限制：多种存储之间存在一致性和运维成本；反思依赖模型判断，不能把每次重写当作事实纠正。SECURITY.md 明确其本地使用定位与网络暴露边界，应用仍须补充授权。

本项目采用分层、来源依赖、增量整理和可编辑思想，把持久数据、索引和版本统一放在现有 SQLite 事务中。重点证据：src/everos/memory/cascade/reconciler.py、src/everos/memory/reflection/orchestrator.py，以及对应单元测试。

## 4. Hindsight：证据与多路召回

技术：以 memory bank 组织 retain、recall 和 reflect，结合语义、关键词、时间和图关系检索，提供租户扩展接口及证据维护。

优势：把“记住的内容”和“从内容形成的认识”区分，来源可支持回溯和撤销；删除和清理测试明确限制 bank 范围，并检查数据库删除次序与锁定。

代价与限制：完整部署引入 PostgreSQL 及相关模型配置，运维负担明显高于本地校园助手；租户扩展点不能代替宿主实际认证和每次查询的所有者条件。

采用证据链、范围前置和融合召回思路。未采用完整 PostgreSQL 服务。重点证据：hindsight-api-slim/hindsight_api/extensions/tenant.py、hindsight-api-slim/tests/test_chunk_storage_delete_ordering.py，以及 consolidation 相关实现。

## 5. MemOS：纠错与版本管理

技术：按 memory cube、用户与工作/长期记忆组织内容；反馈处理可查找、修改、删除记忆并管理历史，后台调度协调多个流程。

优势：对“已有记忆被用户纠正”的处理较完整，不把记忆系统缩减为只增不改的向量表；便于借鉴反馈、替换和历史追踪。

代价与限制：LLM、embedding、图存储和调度器等配置复杂；可写 cube ID 列表是操作输入，不等同于调用者已经通过权限验证。自动纠正仍需要防止覆盖人工修订。

采用待核对替换、历史版本和来源失效处理，增加人工锁定与版本比较。重点证据：src/memos/mem_feedback/feedback.py、simple_feedback.py、src/memos/mem_scheduler/task_schedule_modules/handlers/feedback_handler.py 和相关反馈测试。

## 6. Graphiti：时间语义与图关系

技术：时序知识图谱，检索组合 BM25、余弦相似和图遍历，再以融合或重排处理；边记录断言的有效时间与失效信息。

优势：适合表达事实更新、关系来源和时间变化；源码对事实发生时间与未来计划时间作区分，有助于避免把通知截止日错误当作记忆失效日。

代价与限制：图数据库和模型抽取增加运行成本；错误关系的传播需要额外约束。SECURITY.md 对参考 REST/MCP 服务的认证、授权和租户隔离边界有明确说明，不能直接把示例服务当成已有安全边界。

采用显式有效期、来源版本和派生依赖关系，未引入完整知识图谱。重点证据：graphiti_core/utils/maintenance/temporal_edge_utils.py、graphiti_core/search/search_config.py、SECURITY.md。

## 7. LangMem 与 LangGraph：工具协议和持久状态

LangMem 用结构化工具暴露记忆创建、更新、删除和检索，可通过命名空间模板绑定存储范围；LangGraph 提供执行检查点、命名空间存储与可选 TTL 等底层能力。

优势：操作契约清晰，容易接入已有 Agent；长期存储与一次对话的执行状态分离，重启恢复路径明确。

代价与限制：通用 store.put 或 delete 不天然具备本系统需要的所有者认证、来源证明和乐观版本控制；检查点持久化本身也不会自动生成高质量长期记忆。整体改用 LangGraph 将扩大现有执行链路的迁移面。

采用 remember/update/archive/derive 的受控结构化操作，以及事务化工作记录；在服务器增加所属用户、最新来源和目标版本检查。保留现有执行框架。重点证据：LangMem 的 src/langmem/knowledge/tools.py、reflection.py；LangGraph 的 libs/checkpoint/langgraph/checkpoint/base/__init__.py 和 libs/checkpoint/langgraph/store/base/__init__.py。

## 8. Letta Code：可编辑性与保护

技术：编码 Agent 的 memfs 文件化记忆及权限控制，支持记忆路径识别和只读 frontmatter。

优势：人工能够直接理解和修改记忆；只读边界有利于保护用户明确维护的规则。文件权限逻辑及相关测试可帮助审查 Agent 写入边界。

代价与限制：这是完整编码 Agent 的一部分，不是可以原样放进校园助手的独立记忆库；文件级只读也不等于本系统中的用户、项目、来源、版本权限。

采用人工编辑优先、锁定保护、Markdown 往返编辑与显式工具边界。重点证据：src/permissions/memory-paths.ts、src/memory-frontmatter.ts 及 memfs 相关测试。

## 9. Mem0：写入真实性与版本差异

技术：抽取、向量存储、历史和显式更新删除 API。需要纠正旧介绍中的版本假设：本次快照的自动摄取走 ADD-only 路线，OSS graph 已移除；显式 update/delete 接口仍然存在。

优势：接口简洁，实际成功持久化的记录才进入相应历史；批量删除实现有分批与进度保护，避免一次性大扫描或无进展循环。

代价与限制：不能依据旧文档假定当前版本自动执行复杂增删改决策或完整图记忆；库的 update(id) 不承担本应用 HTTP 调用者的认证责任。

采用“按真实持久化结果发回执”、去重和批量操作边界。未引入其独立向量存储。重点证据：mem0/memory/main.py 的写入、update 与 delete_all 实现，以及本次 README 和迁移说明。

## 10. ReMe：整理流程和检查点

技术：经验记忆、检索和 dream 整理，将多个文件的处理、合并与检查点串联。

优势：注意到整理期间文件可能再次被修改，提交时保留实际观察到的状态；分阶段流程有助于失败重试和后续续跑。

代价与限制：文件大小/时间比较属于尽力检测，不能作为数据库级严格并发控制；高层经验总结也不能直接升级成用户事实。

采用持久作业、分批概览和检查点思想；使用数据库版本号比较避免覆盖编辑。重点证据：reme/steps/evolve/dream/finish.py、integrate.py 及 dream checkpoint 版本测试。

## 11. MemU：让宿主 Agent 负责理解

技术：本次服务接口聚焦 embedding、检索、渐进读取和提交，语义提取交给宿主 Agent；过滤条件是服务接口的一部分。

优势：减少重复建设另一个聊天模型运行时，记忆系统专注可检索存储与渐进呈现；符合现有应用已经具备 Agent 回答链路的条件。

代价与限制：空过滤条件可被接口接受，因此宿主必须主动绑定所有者；宿主输出的抽取结果仍需校验，不能把它视为天然可信的数据。

采用同次回答提出记忆操作、服务器校验执行的分工，未新增后台模型循环。重点证据：src/memu/app/service.py、检索过滤处理与当前 README。

## 12. Memobase：资料与事件分层

技术：以用户画像和事件时间线为核心，利用缓冲区批处理与后台后处理更新资料。

优势：稳定偏好与经历事件分开表示；缓冲批处理可以减少过于频繁的模型整理。

代价与限制：完整服务依赖 PostgreSQL、Redis 和模型处理；用户画像中心的结构不能覆盖本项目所有任务来源、项目隔离和办理证据。上游性能宣传没有作为本机测试结论使用。

采用资料、经历与计划分类型，并把任务状态变化交给持久队列。重点证据：服务的 background.py、post_process/profile.py 与相关用户资料模型。

## 13. Cognee：有界优化作业

技术：图与向量结合的数据处理管线，多数据集权限接口和 improve 优化流程，具备阶段、预算与持久状态。

优势：有助于将后台“变好一点”的工作变成可观察、可恢复的作业；锁与预算限制能减少无限反思或重复执行。

代价与限制：运行依赖和管线规模较大；权限扩展仍要落实到实际存储查询；引入整套图构建与优化会增加当前项目的复杂度和模型成本。

采用可见的队列状态、失败重试、固定每轮上限和无变化不重整。重点证据：cognee/api/v1/improve/improve.py、权限适配器与优化任务测试。

## 14. OpenViking：层次组织与工作记忆

技术：L0/L1/L2 渐进上下文、文件系统式组织和会话工作记忆；工作记忆按固定栏目组织，相关策略默认可关闭。

优势：在上下文预算内分层呈现，工作记忆与长期内容区别明确；实现对大块内联图片输出等内容进行约束。

代价与限制：完整 VFS、索引和服务组合超出当前应用所需。主许可证为 AGPLv3，CLI、示例等部分目录许可不同，README 还有附加说明；不能简单归类为整个仓库均 Apache-2.0，也不能未经审查直接移植改写。

仅参考“原始记录—分类概览—当前工作记录”的抽象层次，未移植源码。重点证据：openviking/session/memory_policy.py、working_memory.py、根目录与子目录许可证、README 的许可说明。

## 15. 最终选型与没有采用的能力

主参考选择 EverOS，因为它同时覆盖可编辑性、长期组织和持续整理；配合 Hindsight 的来源证据、MemOS 的反馈纠正、LangMem 的操作协议、Graphiti 的时间关系、Letta 的人工保护、ReMe/Cognee 的有界持久作业，以及 MemU 的宿主 Agent 分工。具体代码以现有 SQLite 数据模型、FastAPI 权限和聊天发布流程为基础重新实现。

没有启用十三套独立产品，没有引入外部记忆 SaaS，没有运行无上限自动反思，没有把全部历史一次塞进模型，也没有承诺所有自然语言矛盾都能被自动解决。当前完整性指清晰定义的记忆生命周期能够存储、检索、使用、编辑、纠正、整理、审计、导出、失效和遗忘；容量、语义能力与测试范围在实施说明中明确列出。

## 2026-10-21：可靠性 v4 的进一步适配
