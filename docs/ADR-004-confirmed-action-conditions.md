# ADR-004：本人参加意愿、前置步骤与外部条件

状态：在 1.8.0 采用。日期：2026-10-18。

## 实际问题

原 MVP 要求“可选事项由本人决定”，但已有分类只是说明文字：未决定参加的可选事项仍能标记完成，“立项后”也不能约束提交。模型整理与正式办理之间缺少分类和依赖的共同确认接口。

本轮前两次真实模型输出分别在顶层增加 `uncertainties`、把同一 `conditions` 重复放在任务与计划中，导致严格校验拒绝整份结果，耗时分别为 182.812 秒和 233.921 秒，均未创建正式任务。第一次还把组队误认为取得表格的前置，说明结构有效不代表语义有效。失败样本与实际用量保留，不用成功结果覆盖。

## 模型提案与确认事务

模型现在在每项任务旁输出 `action_kind`、`depends_on`、`conditions`，服务器确定性地整理成草稿 `plans`。正式 `TaskData` 保持原结构。兼容旧 `plans` 及完全相同的重复建议；同字段两处冲突则拒绝。已知的全局 `uncertainties` 只接受有界字符串列表并合并到 `warnings`；其他未知字段仍拒绝。模型没有写参加决定、条件状态、核实依据或受理结果的权限。

客户端使用稳定步骤标识，调序、取消选择与恢复缓存不会改变依赖指向；提交前映射为本次选中步骤的序号。未选中或已移除的前置明确阻止保存。服务端在同一事务中分配任务 ID、核对版本、检查全账号依赖图、写办理安排和审计；冲突整批回滚，重复确认返回原 ID。

替换已有待办时默认保留原办理安排。本人明确选择更新分类与前置并提交当前办理版本后，才采用新提案；历史回执、结果和跟进不被覆盖。相同条件保留已核实状态，新条件为待核实。

## 条件语义与历史

可选事项默认不勾选；本人可保存为未决定、参加或不参加。不参加的事项从当前待办、逾期数量和活动日历中排除，仍保留在全部记录中。

每项最多 8 个外部条件，每条 2 至 400 字，状态为待核实、已核实满足或已核实尚未满足。后两者须记录实际依据；这是本人自报，不是学校接口验证。修改条件文本会重置当前核实结果，历史审计保留。多项条件采用全部满足关系；“任选其一”写在同一文本条件中供本人核实。此版本没有通用分支表达式或自动审批执行。

正式提交、受理和标记完成时，检查本人参加意愿、外部条件、前置完成及其条件和复核状态。未来截止提醒可以先于前置完成；自身条件未解决时不能导出正式事项日历，可另建信息核实步骤。信息核实步骤不应依赖它自己正在核实的条件。

已提交或完成后条件变化，允许保存新事实，保留旧回执和历史状态，同时要求复核并传播到后续步骤。保留原进度仍须满足当前本人条件，也可选择重新办理。页面与回答证据均显示未满足条件。条件内容、状态或参加决定改变会增加任务版本，使旧日历和设备验证过时；只改核实说明不增加日历版本。

## 迁移、恢复与取舍

`workflow_schema_version` 从 1 升为 2，旧 JSON 获得空条件列表。主数据仍为 4，记忆 2、执行 1、办理复核 1。旧程序不得忽略条件打开新版本；回退使用旧程序和升级前备份。SQLite 完整恢复保留条件状态与历史；个人 JSON 追加迁移保留条件文字和说明，状态重置为待核实。迁移可重复执行。

事务与状态规则由已有 FastAPI、SQLite 承担，沿用开源审查中显式状态、人工确认、版本记录和回放的机制，不引入完整代理框架、向量服务或新的运行依赖。未来学校接口通过认证适配器提交有来源的事实提案，继续经过权限与版本检查。

没有自动重发失败模型请求。维护者针对已定位协议问题进行的显式真实复验单独记录，不能混为运行时成功率。结构与引用检查无法证明所有业务因果关系正确，人工确认仍是正式写入前提。

## 验证

`tests/test_action_plans.py` 覆盖原子确认、版本冲突、条件证据、历史复核、上下文过时、JSON 导入、旧版本迁移与恢复；`tests/action-plans.test.mjs` 覆盖稳定步骤标识、取消选择、替换保留及活动列表。`scripts/action_plan_preview_server.py` 和 `scripts/verify_action_plans_browser.mjs` 使用隔离合成账号执行三种浏览器的实际 UI、HTTP 与数据库流程。真实模型及最终结果见 [TESTING.md](../TESTING.md)。
