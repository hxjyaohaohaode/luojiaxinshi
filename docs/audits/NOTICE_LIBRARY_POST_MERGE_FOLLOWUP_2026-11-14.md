## 2. 失败发生在哪里

原 `scripts/verify_notice_matters.mjs` 在 Chromium 和 Firefox 各完成7项，在 WebKit 完成前三项。第4项的真实执行顺序是：

1. 成功创建包含两则通知的事项，原始分组卡片可见。
2. 搜索本次合成标记，首次点击“按事项归组”后，两张独立通知卡片均达到可见等待条件。
3. 第二次点击该按钮后，最终等待包含本次标记的 `.matter-library-card` 超时，原时限为12秒。
4. 当前复合检查没有写入完整通过记录；后续并发编辑、移动端/键盘高度、移出解组等三个 WebKit 检查没有执行。

原失败截图显示正确的 `webkit 1794662467539` 查询、已加载3 / 3、展开的筛选区、可见的归组按钮和三张独立通知卡。截图与原报告没有记录当时 `aria-pressed`、pointerdown/up/click 目标或请求完成顺序。因此，不能声称事项创建失败，也不能唯一断定第二次点击历史上发往何处。

## 3. 已证实的控件问题与修复

对未经修改的真实 `createLibraryUI` 和真实 `PagedList` 做受控 Node 观察，保留原180ms去抖与实际控制流：输入查询后旧卡片暂时可见；新查询启动时 collection 清空已加载项，并将原有归组按钮设为 hidden；响应完成后按钮恢复。搜索响应本身没有重置 `grouped`，后续真正送达的切换仍能同步生效。

这证明了**正在使用的显示偏好控件会因读取过程短暂消失**。它是已证的产品交互缺口；Node 的无布局 DOM 没有模拟原生命中测试，不能冒充本次 WebKit 历史事件的完整复现。

最小产品修复仅调整 `static/library.js` 的按钮挂载与隐藏策略：

- “按事项归组”始终留在原有“筛选与来源”折叠区，作为与卡片/列表同类的显示偏好。
- 加载中、空结果、读取失败及当前页没有事项时，不隐藏或禁用该选择。
- 保持同一个活按钮；`aria-pressed` 随本人切换更新。
- 原始筛选、排序、分页、事项元数据、owner授权、账号切换默认值和旧请求拒绝逻辑不变。

新增 `tests/library-controls.test.mjs` 的5项回归使用真实工厂与真实 PagedList。前后使用完全相同的测试字节：旧源5 fail、新源一次5 pass；失败均为具体的按钮缺失或隐藏断言。覆盖首次等待、搜索加载时的同一控件、空/错误/重试、模式保持、账号切换与旧账号迟到响应。既有219个tracked tests条目逐blob未改；新增测试不冒充原生浏览器验证。

事件机制参考：[W3C Pointer Events Level 4，2026-10-08 Working Draft](https://www.w3.org/TR/2026/WD-pointerevents4-20261008/)，§3.3.12.3及§11.3讨论按下/释放目标不同时的click派发。它解释稳定控件为何有意义，不是此次失败的运行轨迹证据；`hidden`也不能等同DOM删除。此前 UI Events 链接的鼠标章节已迁移，正式说明采用这一明确版本并保留草案身份。
