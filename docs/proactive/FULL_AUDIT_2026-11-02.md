# 真实试点全量审计与修复账本

最新演示账号、扫描PDF、办理同步、真实模型恢复与后续回归见 [接续审计](DEMO_CONTINUATION_2026-11-02.md)。下文批次保留当时的结果，不能作为后续修改的最终验收。

本轮承接全部既有要求；范围不是单页或单项测试。主目标为系统主动发现、理解、追踪、分级和提醒，用户选择办理，并可纠正系统误判。学校未提供接口，不把个人办理记录描述成学校正式受理。

## 本轮发现并处理的问题

| 问题 | 实际影响 | 修复及反例 |
|---|---|---|
| 旧输入任务要等到有调用额度才清理 | 等待数量虚高；已撤权来源仍显示排队 | 不计费清理失效/撤权队列；额度耗尽仍生效，失败调用不自动重试 |
| 偏好或头像变化被视为模型条件变化 | 整理中断，可能引起重复付费准备 | 按实际发送模型的个人字段比较；学院变化仍中断，投递偏好不进入模型 |
| 正文更正未同步题名与日期 | 旧题名/旧发布日期一直显示；同文元数据更正遗漏 | 来源稳定身份下版本化元数据更正，保留旧依据；防止转发渠道反复改写主来源 |
| 验证码发送中修改联系方式 | 旧响应丢弃后按钮一直禁用 | 释放按钮、清理旧挑战、提示重发；换账号的旧响应也不能使用 |
| 本地可解析表格，自动采集只读 PDF/DOCX | 常见申请表要用户重新补传 | 显式同域附件共用已有表格/文本/图片解析器；不执行宏，不把 DOC/XLS/ZIP 冒充已读 |
| 关联材料可超出复核源索引范围 | 前段已抓取，后段才结构失败 | 同一预算约束六份来源/五份文件与文字/字节上限，超限保留主文并显示缺口；原四图硬限制已在接续审计中移除，按全部图像/页数计入预算 |
| 复核引用数组允许任意字符串 | 真实模型把原句放进编号数组，整次复核失效 | Schema 约束 R 编号，每份材料提供实际可用编号；不存在/跨源编号仍拒绝 |
| 系统整理被放入用户“需要处理” | 已授权自动处理却让用户逐条核对 | 跟踪中不算用户待处理；个人已选择事项的变更仍保留核对入口 |
| 每个完成任务后固定等待 15 秒 | 积压总等待随条数线性增加 | 有就绪工作继续衔接；空队列才轮询，保留一个交互槽位 |
| 一篇旧内部文章使整栏目持续退避 | 官网公开列表正常，新通知仍延迟数小时发现 | 列表读取成功时维持正常发现间隔；单篇权限失败仍明确展示 |
| 旧比赛的咨询/查结果没有期限 | 已过报名/提交期仍作为新参与机会出现 | 当前、通过核对、原文明确的可选入口全部过期，转为“报名或申报期限已过”；不宣称整件事结束，不完成本人待办 |
| 当前入口关闭可能连带隐藏本人已选工作 | 用户已报名、仍在补件或跟进却难找 | 已选择的待办/跟进继续出现，恢复推荐仍保留原文期限；个人排除另行生效 |
| 管理端只有配置布尔值 | 无法辨别后台任务是否实际启动/退出 | 在原系统维护页显示八项后台任务、队列和渠道配置；管理员只读接口不暴露密钥或用户内容 |
| 已有通知却仍提示“处理第一则” | 引导重复录入，忽视已收资料 | 空待办按真实库存引导去已有通知，由用户选择步骤 |
| 历史信息恢复推荐后仍只能看历史摘要 | 用户纠正已保存，但无法选择原来的办理步骤 | 恢复推荐或已有本人待办时展示原来的可选步骤；保存纠正后即时重绘非编辑页面，编辑表单保留 |
| 已有整理结果缺少重新整理入口 | 复核失败的旧结果无法在当前页面恢复 | 在原通知操作菜单中重新整理，保留服务端原件和本人进度，复用明确的 AI 使用确认 |
| 只有日期的截止显示成次日 | 内部次日零点的失效边界被误当成原文日期 | 只在显示日期精度边界时恢复原文日历日期；精确时刻不改，真实星湖杯显示 4 月 30 日和 8 月 31 日 |
| 完整返回的复核结果结构不合法便终止 | 有可恢复的格式错误但整则处于不可用 | 一个共享四次请求预算内最多一次复核格式补正，仍完整校验真实引用和覆盖；网络失败/超时/截断不自动重放，每次付费前再检查当前输入 |

## 验证口径

后端协调器 `scripts/audit_full_suite.py` 按文件分成最多四个进程，全部测试文件只进入一个分片。每片保留退出码/JUnit/日志，开始和结束核对 app/static/tests 指纹；审计期间的旧批次不能作为最终冻结代码的全绿结论。最终结果只取 `artifacts/full-audit-complete/summary.json`，前端取 `artifacts/full-audit-complete-frontend.log`。补跑批次相互重叠，不相加。`scripts/audit_pilot_snapshot.py --username <本人账号> --local-env` 只读汇总实际资料、队列、配置与验证结果，不发送验证码、邮件、推送或模型请求。

最终后端 103 个测试文件：1,515 通过、1 跳过、0 失败/错误，耗时 531.66 秒，四个分片退出码全为零，开始/结束代码指纹相同。跳过项为 POSIX TIME_WAIT 绑定语义，不在 Windows 上声称覆盖。前端 225 通过、0 失败/取消/跳过。只读汇总再次比较当前 app/static/tests 指纹与最终回归指纹相同。Python 编译检查和 git diff --check 通过。最终 fetch 后 HEAD 与 origin/main 同为 7e1e904、ahead/behind 为 0/0，本地既有和本轮修改均保留，未推送。

真实通知通过已授权来源进入本人的生产代码链路，调用外部模型会产生既有服务用量。本轮上限从此前试用的每天 2 则调为 25 则；没有购买服务器/域名或新开付费资源。真实通知的未完成/复核失败不强制改成通过。采集需要学校登录的页面仍报告缺口，不绕过权限。

## 真实运行结果

- 本人两项官网来源实际刷新；列表读取成功后仍按 30 分钟基础间隔发现新内容，不让单篇权限错误升级为整个栏目的退避。受限文章和未读附件继续显示读取缺口。
- 首次排空历史积压时，19 则真实通知全部有当前版本整理结果，11 则通过独立复核、8 则需核对；没有将其变成个人待办。自动队列当时累计 20 次成功任务、12 次旧输入清退。收尾期间又发现第二号会议通知的来源修订，自动触发第 21 次核对，不需要用户决定是否追踪。后台持续运行，当前版本与任务状态以带生成时间的 `artifacts/full-audit-result.json` 为准；不把一次队列为空当作后续永久没有新任务。自动整理限额为每日 25 次。
- 第 21 次核对完成后的最终快照：19 则都有当前版本整理结果，11 则通过、7 则需核对、1 则独立复核不可用，队列无等待/处理中任务。第二号会议通知的完整复核返回及一次格式恢复仍未通过真实引用/覆盖检查，耗时 203.422 秒、三次实际请求，未自动重试到通过；详情为 `artifacts/full-audit-current-review-gaps.json`。队列 `succeeded` 表示任务完成，不表示内容质量已通过，8 则问题内容不能当作可信的自动办理结果。
- 自动时效投影中，3 则已过原文活动日期、1 则已有据期限经过、2 则报名或申报入口已过；其余缺少充分证据的内容保持未知。6 则退出当前新机会，完整历史可查，用户仍能恢复推荐和添加本人步骤。
- 实际手机操作“恢复推荐”后，不刷新即可显示原来的 10 个可选步骤；验证结束已恢复自动判断、清空测试说明，没有添加个人任务。只有日期的历史截止显示已核对原文日历日期。
- 实际系统维护页显示八项后台任务运行中；这是任务存活证明，不能替代渠道送达。
- 两则复杂会议真实案例耗时 279.406 秒、261.063 秒，均为 Pro 整理 → Flash 独立复核 → Pro 内容补正 → Flash 再复核，共四次请求。初次复核获得有证据的日期/遗漏/适用性问题，最后一次补正复核仍失败，因此保留初次问题，状态仍为需核对。未消耗第五次请求，未宣称复杂通知性能或最终质量已达标。详情在 `artifacts/full-audit-actual-review-outcomes.json`。
- 单独的受控真实模型恢复验证：本地人为拒绝一次已完成的合法复核返回，两次真实 Flash 请求共 10.312 秒，格式恢复通过；这是故障注入，未修改实际通知，也不是整体准确率或自然故障恢复率。详情在 `artifacts/full-audit-live-review-recovery.json`。
- 本轮真实聊天澄清样例首字 4.859 秒、完整 13.72 秒；独立复核确实驳回了错误的 19:00，原文为 18:00。单样例不用于宣称稳定 p95 或整体准确率。
- QQ SMTP 465 连接超时，587 连接中断；认证与收件箱送达均未证明成功。本轮零封测试邮件、零条短信、零条推送。配置值存在不等于通道可用。
- Python 锁定依赖及官方 npm 审计均为零已知漏洞；已扫描可发布的文件未匹配本机配置中的实际密钥值。已知漏洞扫描不代表无所有安全问题。数据库完整性正常、无外键违规。

手机/平板/桌面七个主要页面共 21 个浏览器检查通过，尺寸为 390×844、834×1112、1440×900；无空主体或页面横向溢出。截图与逐页记录在 `artifacts/full-audit-ui/`。本轮真实运行、外部缺口及最终冻结回归统一汇总为 `artifacts/full-audit-result.json`。
